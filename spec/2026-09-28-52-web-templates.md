# Spec: Frontend and backend web templates

## Design

Add two `preset` entries to `data/templates.nix`:

- `frontend`: enable devenv's JavaScript module with npm and the TypeScript
  module. Add `format` and `lint` scripts whose script-local packages are
  `pkgs.prettier` and `pkgs.eslint`. The template supplies Node/TypeScript,
  the language server, a pinned formatter and linter, but no browser framework.
- `backend`: use the same small Node/TypeScript baseline and formatter/linter
  scripts, documented as a service/API starting point. It does not add a
  process or database that would fail before the user creates an application,
  and it does not claim to cover every backend language.

Both entries set `secretScaffold = true`, reusing the shared agenix-compatible
secret files and scripts already generated by the CLI. No top-level `packages`
assignment is added; formatter and linter dependencies stay on their scripts.

The catalogue index, CLI tests, real template runner, README, and usage guide
will list and explain both entries. Notes will point users to Vite, Next,
Astro, Svelte, Express, Fastify, or another framework as an explicit next
choice rather than embedding one in the preset.

The option choices follow devenv's official JavaScript and TypeScript module
documentation:

- https://devenv.sh/languages/javascript/
- https://devenv.sh/languages/typescript/

## Alternatives rejected

- **One generic web template:** rejected because browser and service projects
  have different starting expectations and must remain separately selectable.
- **A framework-specific frontend template:** rejected because choosing Vite,
  Next, Astro, Svelte, or another framework would make the default obsolete
  for users who chose a different stack.
- **A language-neutral backend with many runtimes:** rejected because it would
  install unrelated toolchains and provide no coherent default; Node/TypeScript
  is the smallest backend baseline aligned with the frontend ecosystem.
- **Top-level package lists:** rejected because `devenv init` already writes a
  `packages` assignment and the catalogue forbids a duplicate. Script-local
  packages provide the requested tools without changing that contract.
- **Automatic `npm install`, framework generation, or server startup:**
  rejected because a fresh project has no manifest or application entry point.

## Risks

- Nixpkgs may rename or remove `prettier` or `eslint`; real devenv evaluation
  catches this before release.
- Users may interpret the shared Node/TypeScript baseline as a framework
  choice; labels and notes must state the scope plainly.
- `format` and `lint` are useful only after the project has source files and
  configuration; they must remain inert until the user invokes them.
- The secret scaffold is shared code, so its existing CLI and generated-file
  checks must continue to pass while these entries opt in.

## Verification

- `node --test 'tests/model/*.test.js'`
- Stub CLI tests assert both entries, their notes, script options, and secret
  scaffold metadata.
- `nix flake check --all-systems --no-build`
- `nix run .#templates-check frontend backend`
- Inspect generated `devenv.nix` for the language modules, script-local
  packages, absence of a second top-level `packages`, and encrypted-secret
  files without plaintext values.
